# 媒体下载失败显式重试设计

## 目标

在“同步中心”的媒体下载失败记录中提供明确、可控的重试功能。用户既可以重试单个失败媒体，也可以一次重试归档中的全部失败媒体。显式重试只处理请求时仍处于 `failed` 状态的记录，不干扰正在排队或已经下载完成的媒体。

同时完善 README 和长期维护文档，准确说明现有隐式重试、网页显式重试和命令行重试之间的区别。

## 当前行为

现有 `MediaDownloader.run()` 会处理所有 `status != 'downloaded'` 且来源地址非空的媒体。Likes 同步期间，每收到一批响应都会安排一次下载，采集结束时还会再运行一次下载。因此，较早批次中的失败媒体可能在同一次同步的后续下载任务中被隐式重试。

当前行为有以下边界：

- 同步完成后没有周期性或定时自动重试。
- 服务重启不会自动启动媒体重试。
- 网页只能查看失败记录，不能触发重试。
- `local-favorites retry-media` 会处理全部未下载媒体，包括 `failed` 和 `queued`，范围比本设计的网页显式重试更广。
- 最后一次下载仍失败的媒体会保留在同步中心，等待后续同步中的隐式重试或命令行手动重试。

## 已确认范围

- 同步中心同时提供“全部重试”和每条记录的“重试”按钮。
- “全部重试”处理数据库内的全部失败媒体，不受失败列表最多显示 200 条的限制。
- 单条重试通过推文 ID 和媒体序号唯一定位一项媒体。
- 网页重试只处理 `failed`，不处理已有 `queued` 或 `downloaded` 记录。
- 不增加定时任务、重试次数上限、指数退避或自动服务启动重试。
- 保留现有命令行 `retry-media` 的行为，本次不改变它处理全部未下载媒体的范围。

## 方案选择

采用专用重试接口并复用现有下载器和下载锁。

未采用以下方案：

- 将全部失败项简单改为 `queued` 后调用现有全量下载器。该方案会把原本已排队的媒体一并处理，无法满足只重试失败项的范围约束。
- 从网页启动 `local-favorites retry-media` 子进程。该方案会增加进程管理、状态同步和归档并发风险，不符合现有单进程 FastAPI 架构。

## 后端接口

### 全部失败媒体重试

```text
POST /api/sync/failures/retry
```

接口检查当前同步状态和失败数量。没有活动同步或下载任务且存在失败记录时，创建后台重试任务并返回 HTTP 202：

```json
{
  "state": "retrying",
  "requested": 12
}
```

`requested` 是请求时数据库内全部 `failed` 记录数，不受失败列表查询上限影响。没有失败记录时返回 HTTP 200，`requested` 为 0，不创建后台任务。

### 单条失败媒体重试

```text
POST /api/sync/failures/{post_id}/{media_index}/retry
```

接口仅选择同时匹配推文 ID、媒体序号和 `failed` 状态的记录。接受任务时返回 HTTP 202，`requested` 为 1。记录不存在、已成功或已被其他任务处理时返回 HTTP 404，界面刷新失败列表。

### 忙碌冲突

当同步状态为 `starting`、`collecting`、`downloading` 或 `retrying` 时，两个接口均返回 HTTP 409，不追加重试任务。界面显示当前任务仍在执行的提示。

## 下载选择与状态转换

下载器增加按明确目标集合运行的能力。目标集合由 `(post_id, media_index)` 组成，现有正常同步和命令行入口继续使用默认的全部未下载查询。

网页重试的数据流：

1. 接口只读统计或查找 `failed` 记录，确定请求数量。
2. 后台任务取得现有 `download_lock`。
3. 在锁内重新确认目标仍为 `failed`，并将实际选中的记录更新为 `queued`、清空旧错误。
4. 下载器仅查询目标集合中处于 `queued` 的记录，不包含归档中其他排队项。
5. 每项成功时转为 `downloaded`，记录文件大小、校验值和媒体类型，并清除错误。
6. 每项失败时重新转为 `failed`，写入最新错误信息。

如果任务启动前某项已经不再失败，则跳过该项。下载锁保证正常媒体下载和显式重试不会同时写入相同文件。

## 同步状态

显式重试开始后，全局同步状态进入 `retrying`，并包含：

- `retry_requested`：请求重试数量；
- `retry_downloaded`：本次重试成功数量；
- `retry_failed`：本次再次失败数量；
- `message`：面向用户的中文状态。

前端轮询把 `retrying` 视为活动状态。任务完成后状态进入 `finished`，消息显示本次成功和失败数量。现有 `/api/sync/status` 继续提供归档级 `media_queued`、`media_downloaded` 和 `media_failed`，媒体进度条据此显示实际变化。

发生任务级异常时状态进入 `error`，已完成的单项结果保留；未完成且仍为 `queued` 的选中项必须恢复为 `failed` 并写入任务异常，避免长期停留在排队状态。

## 同步中心界面

### 全部重试

“媒体下载失败记录”标题右侧保留“最多显示 200 条”说明，并新增“全部重试”按钮。按钮规则：

- 失败数为 0 时禁用。
- 正常同步、媒体下载或显式重试进行中时禁用。
- 提交后显示“正在重试…”并保持禁用，直至状态轮询确认任务结束。
- 按钮的可访问名称说明它会处理全部失败媒体，而不只是页面显示的 200 条。

### 单条重试

每个 `.failure-row` 在“查看原文”旁新增“重试”按钮，并把推文 ID 和媒体序号保存在安全的 `data-*` 属性中。点击后：

- 只禁用当前行按钮，并显示“重试中…”；
- API 接受任务后进入全局重试状态，其他重试按钮同时禁用；
- HTTP 404 时提示记录已被处理，并刷新失败列表；
- HTTP 409 时显示当前已有同步或下载任务，不改变失败记录。

### 完成刷新

重试完成后一次并行刷新：

- 同步状态和计数；
- 媒体失败列表；
- 总览统计；
- 当前收藏列表，使刚下载成功的媒体立即显示。

再次失败的记录保留在列表中，并显示最新错误信息。操作消息放在失败面板附近，使用 `role="status"`，不使用浏览器原生弹窗。

## 错误处理

- 请求失败时恢复按钮状态，保留当前列表并显示错误。
- 重复点击由前端禁用和后端 409 双重防护。
- 单条目标已不存在时不视为服务器错误，刷新列表即可。
- 来源链接过期、访问受限、网络超时或媒体不存在时继续保留最新失败原因。
- 重试不会绕过登录、访问控制或平台媒体权限。
- 下载器仍限制并发数，显式重试不新增无限并发。

## 测试策略

### 存储与下载器

- 选择全部失败记录时不包含 `queued` 和 `downloaded`。
- 选择单条记录时严格匹配推文 ID 和媒体序号。
- 选中记录进入 `queued`，成功后为 `downloaded`，失败后恢复 `failed` 并更新错误。
- 目标集合下载不处理集合外的排队媒体。

### Web 接口

- 全部重试返回实际失败总数，不受 200 条列表限制。
- 单条重试只处理指定失败记录。
- 没有失败项时返回零请求结果。
- 活动同步、下载或重试期间返回 HTTP 409。
- 不存在或已处理的单条目标返回 HTTP 404。
- 后台完成后同步状态和归档计数正确。

### 前端契约与浏览器验证

- 页面包含全部重试按钮、单条重试按钮和面板状态消息。
- `retrying` 状态参与轮询和按钮禁用。
- 完成后刷新失败列表、总览和收藏内容。
- 空失败列表时全部重试按钮禁用。
- 通过浏览器构造失败记录，验证单条重试、全部重试、忙碌状态、成功移除记录和再次失败保留记录。
- 检查桌面和窄屏下按钮不会造成失败记录内容重叠。

### 文档验证

扩展项目文档测试，要求 README 和六份长期文档包含显式重试、自动重试边界及命令行范围说明。

## 非目标

- 不增加自动定时重试或服务启动重试。
- 不为每项媒体保存永久重试次数历史。
- 不改变命令行 `retry-media` 的范围。
- 不修改同步采集、推文去重、标签或删除逻辑。
- 不保证已经失效或无权访问的来源媒体能够成功下载。
